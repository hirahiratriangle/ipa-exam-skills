# IPA区分の対策アプリを作る

区分ごとにアプリを1本作る。既存のものを書き換えて区分を移し替えるのではなく、
**必要になった区分のアプリを、そのつど足す**。前の区分のアプリはそのまま残るので、
基本情報を終えて応用情報に移っても、基本情報の記録は消えない。

参照する実装は https://github.com/hirahiratriangle/hirahira_room の `fe/`（基本情報版）。
作る前にこれを読むと、出題ロジックと平滑化の実装が揃う。手元に無ければ
`git clone --depth 1` で作業用の一時フォルダへ取ってきて読む（利用者のプロジェクトには混ぜない）。

## 作る前に確かめること

**区分**（応用情報技術者試験、システムアーキテクト試験、など）と、
**資料を置くフォルダ**。資料が無いと推測で作ることになり、範囲外の分類が入る。

必要なのは3つ。いずれも IPA が無償で公開している。

- **シラバス** — 大分類→中分類→小分類の階層、小分類ごとの学習目標と用語例。
  分類マスタはこれから起こす
- **試験要綱** — 出題範囲の根拠、科目構成、出題数、試験時間
- **公開問題（過去問・サンプル）を過去5年分** — 問題冊子を1問ずつ中分類へ
  振り分けて、想定出題数を実測する。解答例は分野ごとの実数との照合に使う。
  **5年分そろえる。** 1回だけでは、その回にたまたま出なかった中分類が
  0問に見える

## 資料を揃える

資料フォルダは決め打ちしない。依頼の中で指定されたらそこを、指定が無ければ
作業ディレクトリの下に区分名のフォルダ（`応用/` など）を使う。
以降このスキルで「資料フォルダ」と書いたら、ここで決めたフォルダを指す。

1. 資料フォルダを `find . -iname '*.pdf'` で調べ、すでにあるものを確かめる。
   ファイル名と PDF の中身（表紙の「試験要綱」「シラバス」「Ver.」の表記）で
   種類と版を見分ける。ファイル名は IPA の配布名のままとは限らない
2. 足りないものを **IPA のホームページからダウンロードする**（下の節）。
   落とす前に、何を何本、どこへ置くかを利用者に伝える
3. 試験要綱とシラバスは、手元にあっても IPA の一覧ページの版と比べる。
   **IPA のほうが新しければダウンロードする**。同じか手元のほうが新しければ落とさない。
   版はファイル名の `ver5_6`（Ver.5.6）で比べ、手元のファイル名が配布名でなければ
   表紙の Ver. を読む。古い版は消さずに残し、以降は新しい版を使う
4. IPA のサイトに繋がらない、該当の区分が見つからないときは、何が足りないかを
   伝えて利用者に用意してもらう。**資料が揃うまで作り始めない**

PDF は `pdftotext -enc UTF-8 -layout` で読む。入っていなければ
（`command -v pdftotext` で確かめる）、macOS なら `brew install poppler`、
Debian/Ubuntu なら `sudo apt install poppler-utils` を案内する。

## 分野を解析する

| 決めること | どこから取るか |
|---|---|
| 分類マスタ（大分類→中分類→小分類） | シラバスの目次。要綱の出題範囲と同じ階層 |
| 小分類ごとの学習目標・用語例 | シラバスの本文 |
| 頻出計算の型 | シラバスの学習目標と用語例（計算・算出・求める、とあるところ） |
| 科目構成・出題数・試験時間 | 試験要綱 |
| 分野（テクノロジ／マネジメント／ストラテジ）ごとの出題数 | 解答例 PDF。各問に Ｔ・Ｍ・Ｓ が付いている |
| 中分類ごとの想定出題数 | 下のとおり**過去5年分を実測する** |

### 中分類ごとの想定出題数を実測する

中分類ごとの出題数は、シラバスにも解答例にも載っていない。
**区分ごとに、過去5年分の公開問題を中分類に振り分けて数える。**
前の区分の配分を流用したり、別の区分の傾向から推し量ったりしない。
出題の重心は区分ごとに違うので、毎回この調査からやり直す。

手順は、公開問題を**全数**分類することに尽きる。1問ずつ、設問が問うている内容で
中分類を決める。シラバスの小分類の用語例が手がかりになる。そのうえで、
資料の性質に応じて数え方を選ぶ。

#### まず資料の性質を測る

二つの数で決まる。

- **回数** ＝ 集めた問数 ÷ 本番の出題数。何回ぶんの標本があるか
- **刻み** ＝ 本番の出題数 ÷ 1標本の問数。1標本を本番に換算したときの最小単位

| 区分 | 公開のされ方 | 5年で何回分 | 刻み |
|---|---|---|---|
| 応用情報 午前 | 各回80問まるごと、春秋2回 | 10回分 | 1問 |
| 高度区分 午前II | 各回25問まるごと | 5〜10回分 | 1問 |
| 基本情報 科目A | 年度20問＋サンプル60問 | 2.3回分 | 年度3問／サンプル1問 |
| 情報セキュリティ 科目A | 年度一部＋サンプル60問 | 同程度に少ない | 同上 |

通年 CBT の2区分（基本情報・情報セキュリティマネジメント）だけが、年度ごとに
本番の一部しか公開されない。ほかの区分は各回がまるごと公開されるので、
回ごとの分析がそのまま成立する。

#### 数え方を選ぶ

**回数が5回分以上あり、刻みが1問** — 回ごとに分布を出し、その平均を取る。
回を追って傾向が動いていれば、直近に重みを置く。

**回数が足りない、または刻みが粗い（2問以上）** — 単一の集計に寄せない。
性質の違う標本を併用して平均する。基本情報では「サンプルセット60問
（1問刻み・1回分）」と「年度4回ぶんの平均（3問刻み・4回分）」を平均した。
解像度と標本数は裏返しの関係にあり、どちらか一方だけでは偏る。

刻みが粗い標本は、それ単体では傾向の変遷を読めない。基本情報の年度分は
3問刻みで、換算値が0・3・6にしか動かず、1問の差が3問に拡大する。
こういう標本は「毎回出るか、出ない年があるか」という**安定性**の判定に使い、
問数そのものは解像度の高い標本に委ねる。

#### 照合と後処理

- 解答例に分野（Ｔ・Ｍ・Ｓ）の列がある区分は、振り分けた結果の分野別合計が
  解答例の実数と合うかを照合する。ずれていたら振り分けを見直す
- 出題範囲の改訂をまたぐ年度は数に入れない。分類が変わっていて同じ物差しで数えられない
- **合計が本番の出題数と一致する**ように端数を剰余の大きい順に配る
- どの中分類にも**最低1問**を置く。0 だと永久に出題されない
- 推定であることと、**どの年度の何問を数えたか**を分類マスタのコードの注釈に書き、
  利用者にも伝える

#### どこまで精度を求めるか

出題の重みは `想定出題数 ×（0.3 ＋ 2.0 × 苦手度）` で決まる。苦手度の倍率は
0.3〜2.3 倍（未着手はさらに1.6倍）で、配分の差と同程度の効き目しかない。
**±1問を超えて追い込む価値は薄い。** 配分が最も効くのは、全分野が未着手で
苦手度が横並びになる使い始めと、本番比率どおりモードである。

#### やってはいけない数え方

**シラバスの分量で按分してはいけない。** 小分類の数と出題数は対応していない。
基本情報で試算すると、按分ではセキュリティ3問・プロジェクトマネジメント7問に
なるが、実測はセキュリティ7問・プロジェクトマネジメント3問で、ほぼ逆向きになる。
中分類14は小分類が11あるのに本番では3問前後しか出ず、セキュリティは小分類5で
7問出る。按分は手軽だが、重点出題の土台を誤らせる。

**`ipa-questions` が作った JSON の問題数を数えてはいけない。** 問題は配分に
比例して作られているので、数えると元の配分がそのまま返る。完全な循環であり、
一致して見えるのは精度が高いからではない。基本情報で試すと、JSON 全問を
数えた値は元の配分との差が 5.2 問にとどまり、公開問題を全数分類した値
（差 14.0 問）とは別物だった。

**JSON の転記分だけを数えるのも偏る。** どの公開問題を転記するかは、分野ごとの
目標問数を見て選ばれており、図が本質の問題は除外されている。図の多い分野が
実際より軽く出る（基本情報ではハードウェアが 0 問になったが、実際には令和8年度に
出題がある）。

JSON から使えるのは「公開問題の出典 → 中分類」の**対応だけ**である。分類の手間を
省くために再利用してよいが、**公開問題の全数が分類されているかを必ず確かめ、
欠けている問題は設問を読んで埋める**。

**既にあるアプリの配分を、調べ直さずに書き換えない。** 実測に基づく配分が
入っているなら、それを別の方法で置き換えるのは改悪になる。根拠がコードの
注釈に書かれていないなら、数え直して注釈を補う。

### 問題冊子を読む

実測には問題冊子が要る。画像だけの PDF のことがある（応用情報の `_qs.pdf` は
全年度そう）。`pdftotext -enc UTF-8 -layout` で文字が取れないときは、
**OCR ツール（`bunken-ocr-senyo` スキル）をその冊子に合わせてカスタマイズしてから使う**。
汎用のまま流さない。専用スクリプトは区分と冊子の種類ごとに1本作り、年度をまたいで使い回す。

全文を精読する必要はない。中分類を決めるには設問の冒頭だけで足りることが多いので、
**設問の見出しを一覧にしてから振り分ける**と速い。`pdftotext` はページ区切りに
改ページ文字（`\x0c`）を挟み、それが設問行の頭に付くので、行頭一致で拾うと
半分ほど取りこぼす。除いてから数える。

5年ぶんの冊子が無い区分もある。基本情報と情報セキュリティマネジメントは通年の
CBT で、公開されるのは年度ごとの一部とサンプル問題だけである。その場合は
**あるものを全部使う**。集めた問数と、それが何回ぶんに相当するかを利用者に伝える。

**サンプルセットがあるのは基本情報と情報セキュリティマネジメントの2区分だけ**で、
2022年の通年 CBT 移行時に公開されたものである。本番一回分の問数（科目A 60問）が
1問刻みでそろう唯一の資料なので、この2区分では価値が高い。ただし手元で最も古い
資料でもあり、直近の傾向は反映しない。単独で使わず、年度分と併用する。

置き場所に注意する。サンプルセットは公開問題のページ（`mondai-kaiotu`）ではなく、
**シラバス変更のお知らせページ**にある。通常の過去問の導線からは見つからない。
各区分のページ（`/shiken/kubun/<略号>.html`）から「サンプル問題」のリンクを辿る。

    https://www.ipa.go.jp/shiken/syllabus/henkou/2022/20220425.html

出題の重みは苦手度で大きく動くので、配分が1〜2問ずれても出題は大きく変わらない。
ただし、ずれる向きが一方に偏ると（重い分野を軽く見積もるなど）効いてくる。

## IPA のホームページからダウンロードする

PDF の URL は途中に `nl10bi0000009lh8-att` のような推測できない文字列が入り、
改訂のたびに変わる。**URL を組み立てない。一覧ページを取得して、そこにある
リンクを拾う**。ページの場所が変わっていたら https://www.ipa.go.jp/shiken/ から辿り直す。

| 資料 | 一覧ページ | 拾うリンク |
|---|---|---|
| 試験要綱 | https://www.ipa.go.jp/shiken/syllabus/gaiyou.html | `youkou_ver*.pdf`（全区分共通で1本） |
| シラバス | 同上 | `syllabus_<区分>_ver*.pdf` |
| 公開問題（基本情報・情報セキュリティマネジメント以外） | https://www.ipa.go.jp/shiken/mondai-kaiotu/index.html から年度別ページ（`2025r07.html` など） | `<年度><期>_<区分>_*.pdf` |
| 公開問題（基本情報・情報セキュリティマネジメント） | https://www.ipa.go.jp/shiken/mondai-kaiotu/sg_fe/koukai/index.html から年度別ページ | そのページにある該当区分の問題と解答例 |

公開問題のディレクトリ名は `mondai-kaiotu`（IPA 側の綴りのまま。`kaitou` ではない）。

**区分の略号** — ip（ITパスポート）、sg（情報セキュリティマネジメント）、fe（基本情報）、
ap（応用情報）、st・sa・pm・nw・db・es・sm・au（高度の各区分）、sc（情報処理安全確保支援士）。
高度区分の午前I は全区分共通で `koudo` の名前になっているので、区分の略号と併せて拾う。

**ファイル名の読み方** — `2025r07a_ap_am_qs.pdf` は 令和7年度・秋期（`a`。春期は `h`）・
応用情報・午前・問題冊子。末尾は `qs`（問題）、`ans`（解答例）、`cmnt`（採点講評）。
3種とも落とす。解答例が無いと正解を照合できない。

```
UA='Mozilla/5.0'
base=https://www.ipa.go.jp
curl -sL -A "$UA" $base/shiken/mondai-kaiotu/2025r07.html \
  | grep -oE 'href="[^"]*_(ap)_[^"]*\.pdf"' | cut -d'"' -f2 | sort -u \
  | while read -r path; do curl -sL -A "$UA" -o "資料フォルダ/過去問/$(basename "$path")" "$base$path"; sleep 1; done
```

- **どこまで遡るか** — **直近5年ぶんは必ず落とす**。想定出題数の実測に要る。
  現行の出題範囲になってからの年度を、新しい順に。出題範囲の改訂をまたぐ年度は
  数に入れない（分類が変わっているので、同じ物差しで数えられない）。
  5年に満たない区分はあるものを全部。作問にもっと要る、全年度が欲しいと
  言われたら足す
- **ファイル名は配布名のまま保存する** — 年度・期・区分・種別が名前から分かり、
  出典フィールドにそのまま使える。シラバスと要綱は資料フォルダの直下、問題は `過去問/` に置く
- **間をあけて取りにいく** — 1本ごとに1秒。並列で一気に落とさない
- **落としたあと確かめる** — 本数が一覧ページのリンク数と合うこと、どれも `%PDF` で
  始まること（エラーページの HTML を `.pdf` で保存していないこと）。シラバスと要綱は
  表紙の Ver. を読み、どの版を使うかを利用者に伝える
- 基本情報と情報セキュリティマネジメントは通年の CBT で、公開されるのは年度ごとの
  一部の問題とサンプル問題だけ。あるものを全部落とす

## 作るもの

利用者の Django プロジェクトに、アプリを1つ足す形。サーバもDBも増やさない。
プロジェクトが無ければ、`django-admin startproject` で最小のものを作ってから足す。
どちらにするか、どこに作るかは作り始める前に確かめる。

参照実装の `fe/` は、載っているサイトの次のものに頼っている。コピーしたり
真似たりするなら、利用者のプロジェクトにあるかを確かめ、無ければ用意する。

- **`base.html`** — テンプレートはすべて `{% extends 'base.html' %}`。Bootstrap 5 と
  Font Awesome 5 を読み込み、`title`・`head`・`header`・`contents`・`extra_js` の
  ブロックを持つもの（`content` ではなく `contents`）。上部に固定ナビバーがある前提で、
  ヘッダーに `padding-top: 5rem` を入れている。ナビバーが無ければ詰める
- **ログイン** — ビューは `LoginRequiredMixin` を継承し、`LOGIN_URL` は django-allauth の
  `account_login`。ログインの仕組みが無いなら、`django.contrib.auth.urls` を足すか、
  ミックスインからログイン必須を外す。どちらにするかは利用者に聞く
- **設定値** — `FE_MAX_UPLOAD_BYTES`（取り込みの上限。8MB）と、それより大きい
  `DATA_UPLOAD_MAX_MEMORY_SIZE`。区分ごとに接頭辞を変える
- **管理画面** — 管理用の ID は Django の管理画面で付ける。`createsuperuser` まで案内する
- **管理コマンドの名前** — `seed_fe`・`purge_temp_learners` のような管理コマンドは、
  **区分ごとに名前を変える**（`seed_ap`・`purge_temp_learners_ap`）。コマンド名は
  プロジェクト全体で1つで、同じ名前が2つのアプリにあると、`INSTALLED_APPS` で先に
  並んだほうだけが動く。エラーにならないので、あとから足した区分の掃除が
  黙って効かなくなる。テストで `call_command` して確かめる

1. **分類マスタ** — シラバスの階層をそのまま写す。IPA の区分はどれもシラバスが
   あるので、自分で分類を起こす必要はない
2. **想定出題数** — 中分類ごとの出題数は IPA が公表していない。
   過去5年分の公開問題を中分類に振り分けて数える（「分野を解析する」の節）。
   区分ごとに毎回調べ直し、**合計が本番の出題数と一致する**ようにする
3. **計算問題のテンプレート** — 数値を変えれば何度でも解ける型。区分ごとに頻出計算が違う
4. **出題ロジック** — 下の節
5. **画面** — 1問1答の演習、解説を読んでから解く学習モード、
   分野別の正答率、解答履歴、出題設定
6. **テスト** — 重点出題が実際に苦手分野へ寄ることを検証する

**このスキルでは問題と技術解説は作らない。** アプリは JSON を取り込む口を持つところまで。
中身は別に作る。問題は `ipa-questions` スキル、技術解説は `ipa-notes` スキル。

## 出題ロジック

分野を選ぶところと、その中で1問を選ぶところの2段になっている。

### どの分野から出すか

```
重み ＝ 想定出題数 ×（0.3 ＋ 2.0 × 苦手度）
```

本番比率だけで出すと、得意になった分野も同じ頻度で出続ける。
苦手度だけで出すと、本番で1問しか出ない法務ばかり出る。
掛け合わせると、本番の重みを保ったまま苦手が厚くなる。得意なら0.3倍、
まったく解けないなら2.3倍。未着手の分野はさらに1.6倍する。

### 苦手度をどう測るか

素の正答率をそのまま使わない。2問解いて2問外しただけで正答率0%になり、
その分野ばかり出るようになってしまう。

```
平滑化した正答率 ＝ (正解数 ＋ 5 × 0.6) ÷ (解答数 ＋ 5)
苦手度 ＝ 1 − 平滑化した正答率
```

合格ライン相当の 0.6 へ、5問ぶんだけ引き寄せてから比べる。
解答数が増えるほど平滑化の影響は小さくなり、実測値に近づく。

### 分野の中でどの問題を出すか

未出題を常に最優先にすると、落とした問題は未出題が尽きるまで戻ってこない。
200問あれば全部を一度ずつ解き終わるまで復習されない。

そこで**まちがえた問題は、ほかを数問はさんでから未出題より先に戻す**。
直後に出すと答えを覚えているだけで解けてしまうので、間はあける。
何度も落としている問題ほど間隔を詰める（5問 → 3問 → 2問）。

未出題も期限の来た復習も無いときは、正解済みで久しく解いていないものを回す。

## データの持ち方

成績は**アプリ内の ID（Learner）ごと**に持つ。サイトの
アカウントとは紐づけない。ID は本人が決める文字列で、セッションが覚え、
ダッシュボードは /fe/<ID>/ で開く（ほかの ID のものは404）。
URL の接頭辞は区分ごとのアプリ名にする（応用情報なら /ap/ など）。
合言葉は無く、ID を入力した人を本人として扱う。

**ID の登録を必須にしない。** 入口で「履歴を残す／残さない」を選ばせ、
ID の入力欄は「残す」を選んだ中にだけ置く。ID を決めるところが最初の関門になると、
試しに使いたいだけの人がそこで止まる。

履歴を残さない利用は、**code を空にした Learner** として持つ。セッションだけが
参照を持ち、URL からはたどれないので、入口（/fe/）がそのままダッシュボードになる。
苦手重点の出題も学習モードも成績の積み上げが要るので、使っている間は登録 ID と
まったく同じ仕組みで記録する。「いっさい記録しない」作りにすると、このアプリの
中心である重点出題が成立しない。

決めておくことが三つある。

- **引き継ぎ** — あとから ID を登録したとき、それまでの解答を引き継ぐか。
  引き継がない作りのほうが単純で、どの記録が残るかを使う人が追いやすい。
  どちらにするかは利用者に聞き、登録画面に明記する
- **全体集計からの除外** — いずれ消える記録を合計に数えると、あとで総数が減って
  辻褄が合わなくなる。のべ解答数・利用者数は登録 ID だけで数える。
  合格申告のように実績として残る操作は、ID の登録を必要にする
- **掃除** — 誰も参照しない記録が増え続けないよう、最終利用からの日数で消す
  管理コマンドを置く（`last_seen_at` を持たせ、画面を開くたびに進める）。
  登録 ID には触れない。コマンド名は区分ごとに変える（「作るもの」の節）

ID があることを前提にしたテンプレートに注意する。`{% url 'fe:dashboard' learner.code %}`
は code が空だと `/fe/None/` になり、`{{ learner.code }}` は「None」と表示される。
アプリ内だけでなく、サイト共通のヘッダーまで含めて洗い出す。

**問題と解説は全 ID で共有**し、JSON の取り込みで更新する。
JSON は `ipa-questions`（問題）と `ipa-notes`（技術解説）のスキルで作るもので、利用者が
自分で用意することはない。そこで取り込み・
書き出し・問題の一覧は**管理用の ID（is_admin）だけ**に許し、ほかの ID には
画面の入口も出さない。管理用にするのは Django の管理画面から。
画面に入力欄は置かない。更新経路をファイルに絞ると、手元のファイルと
出題内容がずれない。

### 学習モードの出題範囲

**出題は、読んだ解説と同じ小分類だけにする。** 10問に足りないからといって同じ
中分類から補ってはいけない。読んでいない小分類の問題が混ざると、ラウンドの
正答数が「読んだ範囲が身についたか」を表さなくなる。1ラウンドの問数は解説ごとに
変わってよい。基本情報の実データでは、解説1本あたりの対応問数は中央値3問だった。

この制約は**解説と問題の対応を見えるようにする**ことと対になる。解説ごとに
出題できる問数を一覧に出し、0問の解説は選べないようにする。おまかせも0問の解説を
選ばない。選ぶと、読ませたあとに出題できず始められない。

**学習対象は中分類でも選べるようにする。** 解説1本は小分類なので、「この分野を
やりたい」に対して粒度が細かすぎる。中分類を選んだら、その中の未読から選ぶ。

**ダッシュボードで分野を指定しているなら、それを初期選択にする。** 指定が無ければ
何も選ばない（そのまま送ればおまかせ）。ただし科目を切り替えた直後など、その分野で
学習できないときは選ばない。選べない行を選んだ状態にすると、そのまま送ったときに
何が起きるかが画面と食い違う。

**中分類の中の解説は、シラバスの小分類の順に並べる。** 並びの正はシラバスに置き、
中分類ごとの小分類とその順を**分類マスタに持つ**。取り込んだ順に頼ってはいけない。
取り込みは同期なので、あとから1本足した解説は末尾に付く。基本情報では、
手元の notes の JSON 自体が2か所でシラバスと違う順になっていた。
小分類名の文字順はもっと悪く、「プロジェクトのコスト」が
「プロジェクトマネジメント」より先に来るように崩れる。
シラバスに無い小分類は末尾に回す。

### 取り込みは同期にする。全差し替えにしない

**問題と解説は別のファイルにし、別々に更新できるようにする。**
問題は作問のたびに何度も入れ替わるが、解説はほぼ固定で、苦戦している分野だけ
あとから書き足す。更新の頻度がまるで違うものを1ファイルに縛ると、問題を1問
足すために解説を全部運び直すことになり、取り違えれば相手側が消える。

受け付ける形は3つ。`{"questions": [...]}` だけ、`{"notes": [...]}` だけ、両方入り。
**ファイルに入っていない側は触らない。** 解説を含まないファイルを取り込んでも
解説は消えない。

そのためには、**「空の配列が入っている」と「キーごと無い」を区別して持つ**必要が
ある。空の配列を「0件に同期する」と読むと、全消しになる。どちらか分からない形で
持つと、入っていない側に触らないという約束を守れない。空の配列は取り違えを疑って
弾くほうがよい。

**取り込みの画面も、問題と解説で欄を分ける。** ファイルを2本に分けても欄が1つの
ままだと、2本入れるのに2回の操作が要り、別々に渡せること自体が画面から読み取れない。
どちらの欄も任意にして、片方だけでも両方同時でも取り込めるようにする。
両方の欄に同じ側（問題なら問題）が入っていたら、どちらを使うか決められないので弾く。
検証は2本ぶんをまとめて行い、1件でも通らなければどちらも書き込まない。

取り込みは全差し替えではなく、**鍵で突き合わせて追加・更新・削除する同期**にする。

| | 突き合わせの鍵 | 更新として扱う変更 | 別物として扱う変更 |
|---|---|---|---|
| questions | subject ＋ category ＋ stem（空白を正規化） | choices・answer・explanation・difficulty・topic・source | stem の文言 |
| notes | category ＋ title | body・topic・source | title |

**ファイルに無い行は消す。** 追記だけにすると、アプリの中身と手元のファイルが
ずれていき、どちらが正か分からなくなる。結果は全差し替えと同じで、変わっていない
行だけが生き残る形になる。

同期にする理由は、出題の選び方が問題ごとの解答履歴に乗っているため。未出題を先に
出し、まちがえた問題は他の問題を何問かはさんでから戻し、何度も落とした問題ほど
間隔を詰める。全差し替えにすると、取り込んだ瞬間に全問が未出題に戻り、復習の
待ち行列も間隔計算の土台も消える。問題を足すたびにこれが起きる。解説も同じで、
全消ししてから入れ直すと「どの解説を読んだか」の履歴（学習モードのラウンドが指す
解説）が毎回切れる。

確定の前に**件数を見せる**。

```
問題：追加 60 / 更新 3 / 変更なし 234 / 削除 0
解説：変更なし 82（ファイルに解説が含まれていません）
```

全差し替えでは「削除 237」が常態なので異常に気づけないが、同期なら削除の件数が
事故の警報になる。あわせて、ファイル内で鍵が重複していたらエラーにし（どちらが
勝つか不定になる）、削除が既存の3割を超えるときは確認を1枚はさむ。

**残すのは分野ごとの理解度**（解答数・正解数・最終解答日）で、解答のたびに
別テーブルへ積み上げる。鍵が変わって別物になった問題の履歴は消えるが、苦手判定は
こちらに積まれているので続く。

分類マスタと計算問題のテンプレートはアプリ全体で共有する。

## 画面

- **入口（/fe/）** — 履歴を残す／残さないを選ぶ。残す場合だけ ID を入力して入る・新しく作る。
  履歴を残さず始めた人には、ここがそのままダッシュボードになる
- **ダッシュボード（/fe/<ID>/）** — 全体の正答率、苦手な分野、未着手の分野、学習日数
- **1問1答** — 出題モード（おまかせ／本番比率どおり／苦手分野だけ／復習／分野指定）
- **学習モード** — 技術解説を時間を決めて読み、そのあと**読んだ解説と同じ小分類の
  問題だけ**を最大10問。読む段階では設問も選択肢も見せない。答えを覚えるのでは
  なく中身を読ませたいため。選ぶのは中分類（その中の未読から）か解説の1本
  （「学習モードの出題範囲」の節）
- **分野別の正答率** — 中分類ごとの成績と、重点出題での比率
- **解答履歴** — まちがえた問題を見返す
- **問題の管理**（管理用の ID のみ） — 一覧と JSON の取り込み・書き出し。
  取り込みの画面は、問題と技術解説でファイルの欄を分ける（どちらも任意）

どのページにも同じヘッダーを置き、どこからでも同じ場所へ戻れるようにする。

**対応していない問題・問題形式は、入口とダッシュボードの最上部に畳まずに書く。**
このアプリは択一しか出せないので、記述式の科目（応用情報の科目B など）は設問を
択一に直したものになり、記述する力は測れない。図が本質の問題も載らず、本番どおりの
通しの模擬試験も無い。知らないまま進めると、本番との差に試験当日まで気づけない。
文面は1つの部品にまとめ、区分ごとに中身を書き換える。

## 分析の単位は中分類

情報処理技術者試験の出題範囲は、分野（3）→ 大分類 → 中分類 → 小分類 の階層。

小分類は細かすぎて、解答数が貯まらず正答率が安定しない。
分野は粗すぎて、次に何を勉強すべきかが決まらない。
**中分類**なら、弱点が分かれば次の一手が決まる。基本情報で23個。

## 一度に頼むなら

```
IPAの◯◯試験の対策アプリを作ってください。試験要綱・シラバス・公開問題の PDF は
IPA のホームページからダウンロードしてください。既存の Django プロジェクトに追加してください。

1. シラバスの階層を、そのまま分類マスタにする
2. 過去5年分の公開問題を中分類に振り分けて数え、想定出題数にする
   （合計が本番の出題数と一致するように）。シラバスの分量での按分はしない
3. 数値を変えれば何度でも解ける計算問題はテンプレート化する
4. 出題は重み付き抽選にする。重み ＝ 想定出題数 ×（0.3 ＋ 2.0 × 苦手度）
   苦手度は、正答率を 0.6 へ 5 問ぶん平滑化してから求める
5. 1問1答の演習、解説を読んでから解く学習モード、分野別の正答率、
   解答履歴の画面を作る
6. 入口では、履歴を残すかどうかを選べるようにする。ID の登録は「残す」を
   選んだときだけ。残さない利用でも、使っている間は重点出題と学習モードが
   使えるようにする
7. 重点出題が実際に苦手分野へ寄ることを、テストで検証する
```

## 区分ごとに違うところ

基本情報のものをそのまま持ってくると、次が合わなくなる。

- **中分類と想定出題数** — 区分ごとに違う。シラバスと解答例から起こし直す
- **科目の呼び方** — 基本情報は科目A／科目B。応用情報と高度区分は、令和8年度
  （2026年度）の CBT 移行で「午前・午後」から「科目A・科目B」（高度は科目A-1・A-2・
  B-1・B-2）に改称された。公開問題のファイル名と冊子は午前・午後のまま。
  どの呼び方にするかは、その時点の要綱で確かめる
- **中分類ではない分類の番号** — 科目B（旧午後）のように、中分類とは別の軸で分野が
  決まっている科目がある。番号は**要綱の表の並びのとおり**に振る（応用情報なら別紙
  「科目B試験の分野別出題数」の並びで 101〜111）。公開問題の問番号順で振らない。
  要綱が問番号を決めているのは一部だけで（応用情報なら問1＝情報セキュリティ）、
  残りは年度の実績にすぎない。**アプリの分類マスタの番号が正**で、作問スキル側の
  JSON はこの番号で分野を指す。両者が食い違うと取り込みは通ってしまい、見出しと
  中身がずれて表示される。番号と名前の対応はテストで固定する
- **記述式・論述式の科目** — 択一に直して出すのか、対象外にするのかを利用者に聞く。
  出すなら、画面の注意書きに「本番は記述式」と書く（「画面」の節）
- **計算問題の型** — 頻出の計算が違う
- **画面の見出し** — 「FE 基本情報対策」のような文字列が各所にある

一方、分野（テクノロジ系・マネジメント系・ストラテジ系）は共通キャリア・
スキルフレームワークのもので、どの区分でも同じ。ここは触らなくてよい。

## 公開して運用する

既存サイトにアプリを1つ足す形なので、デプロイ先も増えない。
サイトにログインの仕組みがあれば、全画面ログイン必須にする（入口で締める）。
そのうえで成績はアカウントではなくアプリ内の ID ごとに分ける。
公開しない、自分の PC だけで使うなら `runserver` で足りる。

問題データをコードから切り離しておくと、あとで作り直すのも他の区分に
流用するのも楽になる。**貯めるのは成果物ではなく、作り方**。
